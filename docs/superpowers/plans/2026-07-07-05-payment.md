# Phase 05 — Payment Service Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The Payment service turns approvals into money movements with provable consistency (M9/M10): a persisted-step saga (reserve budget via ETag CAS → execute via mock provider → compensate on failure), the M12 defense-in-depth ceiling re-check, budget seeding from the fixture file, deterministic failure injection (double-gated) for journey D, and the no-overspend concurrency guarantee (INV-1014A/B) — all proven over real sidecars in the compose smoke, with Redis hardened per D-017 (AOF + volume).

**Architecture:** Spec §6, decisions D-014 (saga mechanics: step-marker, CAS budgets, injection, integer cents), D-015 (own keys: `saga:*`, `budget:*`, `provider:*`, `processed:*`), D-016 (afcommon dedupe + forget pattern), D-017 (budgets on hardened Redis). **Binding contract notes from Phase 04:** `approval-resolved` is AT-LEAST-ONCE per invoice with FRESH event_ids — saga idempotency MUST key on `invoice_id`, and the suite MUST test a double `approval-resolved` with different event_ids; the payload now carries `usd_cents` (amount for human-approved items); `decision-made` carries `usd_cents` + `ceiling_cents` (auto items).

**Tech Stack:** Python 3.12 · FastAPI · pydantic v2 · afcommon · Dapr pub/sub + state · Redis (AOF).

## Global Constraints

- Money is integer cents; the saga never recomputes amounts — `usd_cents` comes from the triggering event.
- Saga progress is a persisted record (`saga:{invoice_id}`): `started → reserved → paid | compensated | rejected_insufficient_budget`. Crash-safety = resume from the marker; "progress is a record, not a process."
- Budget mutations ONLY via ETag CAS loops (afcommon `cas_update`); budget can never go below zero — assert as an invariant in every budget test.
- Failure injection double-gated: `FAILURE_INJECTION_ENABLED=true` (compose/test only, default off in code) AND invoice `scenario` startswith `payment-failure` — the scenario field rides the DecisionMadePayload? NO — payment never sees the submission. Resolution (document in code): intake includes the fixture's `scenario` field in the invoice dict inside `invoice-submitted`; decision passes NOTHING — so payment gets the marker via a `scenario: str = ""` field ADDED to DecisionMadePayload and ApprovalResolvedPayload (default "", backward-compatible), populated by decision-svc from the invoice (decision touch: one line in pipeline) and by approval from a new `scenario` field on Escalation. This is the minimal wiring that keeps journey D self-triggering from the fixture file. (Contract addition mirrors Phase 04's usd_cents precedent.)
- Dedupe: afcommon EventDedupe, decision-svc pattern (mark → process → forget-on-failure → 500); BUT saga idempotency is per-invoice via the saga record — event dedupe is an optimization, the saga marker is the guarantee (at-least-once contract).
- Branch `feature/payment` off `main`; conventional commits; controller pushes per task; PR at end. Baseline: **253 passed**.
- Relative imports in src/; no noqa; installed-package imports.

### Task 3: The saga — provider, step-marker, compensation, ceiling re-check

**Files:**
- Create: `src/provider.py`, `src/saga.py`
- Test: `tests/test_provider.py`, `tests/test_saga.py`

**Interfaces:**
- `provider.py`: `PaymentDeclined(Exception)` · `MockPaymentProvider(store, injection_enabled: bool)` with `async execute(invoice_id, amount_cents, scenario: str) -> str` (payment ref): idempotency record `provider:{invoice_id}` FIRST-write (retry returns the SAME ref, no double execution); if `injection_enabled and scenario.startswith("payment-failure")` → raise `PaymentDeclined` BEFORE writing the record (a declined payment must be retryable after the cause clears — but for journey D it stays declined).
- `saga.py`: `SagaState` StrEnum (`started, reserved, paid, compensated, rejected_insufficient_budget`) · `SagaRecord` (invoice_id, correlation_id, state, department, amount_cents, payment_ref, failure_reason, updated_at) · `PaymentSaga(budgets, provider, store, publisher)` with `async handle(invoice_id, correlation_id, department, amount_cents, scenario, *, auto_route: bool, ceiling_cents: int | None) -> SagaRecord`:
  1. Load `saga:{invoice_id}` — terminal state → return it unchanged (per-invoice idempotency, THE at-least-once guarantee; also covers double approval-resolved with fresh event_ids).
  2. Guard (M12 layer 4): `auto_route and ceiling_cents is not None and amount_cents > ceiling_cents` → refuse loudly: publish `payment-failed{reason="ceiling-violation", compensated=False}`, state=compensated with failure_reason, log.critical. (Second service must also be wrong for money to move.)
  3. `started` → save marker → `reserve()`: False → `rejected_insufficient_budget` + publish `payment-failed{reason="insufficient_budget", compensated=False}`.
  4. `reserved` → save marker → `provider.execute()`: `PaymentDeclined` → `release()` + `compensated` + publish `payment-failed{reason, compensated=True}` (journey D: reserve→fail→release, no orphaned reservation).
  5. Success → `paid` + publish `payment-completed{amount_cents, budget_remaining_cents, department}`.
  6. Crash-resume: `handle` called with an existing NON-terminal marker resumes from it (`started`→ step 3; `reserved` → step 4 — provider idempotency makes the retry safe).
- Department comes from the invoice… payment doesn't have the invoice. RESOLUTION: `DecisionMadePayload` already carries nothing about department — ADD to Task 1's contract change: `department: str = ""` on both payloads, populated exactly like scenario (decision from invoice, approval from escalation via a new Escalation.department — from_decision reads `payload.department`). Task 1 implementer: include department alongside scenario everywhere. (Escalation already HAS a category field but department is distinct — add it.)

- [ ] **Step 1: Failing tests.** Provider: execute once → ref; execute again same invoice → SAME ref, one record · injection: enabled+marker → PaymentDeclined, NO record (retry still declined while marker present) · disabled+marker → normal success (the double gate) · enabled+no-marker → success. Saga: happy auto path (guards→reserve→execute→paid, events asserted with correct payloads) · human path (auto_route=False skips ceiling check even if amount > ceiling — human approval IS the authorization) · ceiling violation on auto → refused, budget untouched, log.critical, payment-failed(ceiling-violation) · insufficient → rejected + event, budget unchanged · declined → compensated, budget RESTORED (assert exact), payment-failed(compensated=True) · terminal idempotency: handle twice → one reserve, one execute, second returns cached record, NO second event · **double approval-resolved simulation: two handle calls with different event contexts → exactly one payment (the binding at-least-once test)** · crash-resume from `reserved`: marker pre-seeded, handle → executes + paid without double-reserve (budget decremented ONCE — assert).
- [ ] **Step 2: RED.** **Step 3: Implement.** **Step 4: GREEN + gates.**
